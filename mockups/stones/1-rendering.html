Three ways to draw a stone

The same six stones, drawn three ways. Each stone is one idea a learner has proven: its shape, material and finish are decided by the system on board 2, so the only thing that changes here is the drawing method.

Numbers marked “measured here” are timed in this browser when the page loads, so they change with the device you open it on.

A. Drawn by code as vector art

A small engine turns four values (cut, material, finish, seed) into an SVG: flat facets shaded by a fixed light, gradients for inner glow and gloss, one blur filter for the pebble highlight. It extends the recipe renderer already in the app, which ships a stone as an SVG inside an image tag.

Download size
of code, no image files. Each stone is built on the spot.
Speed
(measured here). The browser paints each stone once, then scrolls it as a bitmap. Fine on a phone.
Hundreds of unique stones
No extra cost. 288 named combinations and any number of seeds come from the same code.
Accessibility
A normal image with the stone's name and meaning as its text. Sharp at any zoom. No motion.
Needs from an image model
Nothing.
Weak point
Reads as a fine illustration, not a photograph. The light does not move.

Fit with today's code: the recipe schema stores a model-written SVG capped at 4,000 characters. These stones are characters each, so the better fit is to store the four values and let the engine draw, not to store the SVG.

B. Lit live, following your pointer

A WebGL shader computes real facet angles for the same shapes and lights them from wherever the pointer is. Move across the row: facets flash, the glow inside the moonstone drifts, and the star in the baton slides with the light, as it does in a real star stone.

Download size
of shader and glue, no image files.
Speed
(measured here). Comfortable for a handful of stones on a mid-range laptop. On a phone, redrawing a whole wall every frame costs battery, so it should only redraw while the light moves.
Hundreds of unique stones
Same values as A, so no extra art. But browsers allow about 16 live WebGL canvases, so a wall must share one canvas, and .
Accessibility
A canvas says nothing to a screen reader, so every stone needs a text twin. The pointer effect does nothing for touch or keyboard users unless tilt or drag is added. Holds still under reduced motion.
Needs from an image model
Nothing.
Weak point
Does not work without WebGL, so A has to exist anyway as the fallback. Two renderers to keep looking alike.

C. Photographed once, varied by code

An image model makes one picture per stone family, and code varies it: a hue shift per stone, a matte veil for a fresh cut, glints for the higher finishes. This is how the seven stones in the app are made today.

These six are stand-ins, and their shapes are wrong on purpose. The project's Gemini key is on the free tier, where image generation has a quota of zero, so I could not generate plates for the new cuts. What you see is four of the app's existing images recoloured and finished by code, which shows the method honestly. The prompts for the real plates are at the bottom of this section.

Download size
Today's images are 5 to 22 KB each at 320 px. One per family (6 cuts by 12 materials = 72) is about 1 MB, loaded as you scroll. A sharp large stone needs a second, bigger file.
Speed
The cheapest of the three while running: plain bitmaps.
Hundreds of unique stones
Every new cut or material is a paid batch plus a person checking it. Finishes either multiply the files by four or are faked with overlays, as here. A photo cannot be split into shards, so the forming state needs yet another drawing.
Accessibility
Same as A: an image with text. Goes soft when zoomed.
Needs from an image model
A paid image tier, a fixed reference image so angle and light match across 72 plates, background removal, and review. Three of today's seven images came back with a background baked in.
Weak point
Consistency. The set looks like a system only if every plate matches, and the model does not promise that.

Recommendation

      
Build A as the foundation and use B for one stone at a time.

    

    

      
A draws every stone everywhere: the wall, lists, the forming state, the share image. It is the only direction that can show a stone half-made from its shards, costs nothing per new stone, and is an ordinary labelled image for anyone using a screen reader.

      
B is where the pleasure is. Use it only where a single stone is the subject: the moment it forms and the detail view on the wall. Both read the same four values, so a stone looks like itself in either. When WebGL is missing the stone simply stays as A.

      
Leave C. It gives the richest single image, but it cannot show shards or finishes without many more files, and keeping 72 plates consistent is ongoing paid work.
